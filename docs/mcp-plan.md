# MCP в Sculptor — план

Версия 1.0 от 2026-10-02. Статус: согласование, код не начат.

Цель: Claude Code подключается к запущенному Sculptor и правит префабы,
воксельные объёмы, анимации и стейт-машины. Нужно для ускорения производства
контента к MVP.

## 1. Исходное состояние

- **Основа есть.** Около 40 операций с undo (`apps/sculptor/src/operations.cppm`),
  шесть сервисов, стейт-машины `.voxf` уже существуют и правятся в редакторе.
  Все четыре формата (`.vox`, `.voxm`, `.voxa`, `.voxf`) текстовые.
- **Ошибок не существует как канала.** Все `execute()` возвращают `void`,
  холостая операция попадает в undo. Многие операции берут узел через
  `name_to_entity[name]`: несуществующее имя вставляет в карту пустую сущность,
  дальше неопределённое поведение. Контекст правки не проверяет ни одна операция.
- **Часть действий живёт только в модалках.** Создание и открытие префаба
  (`new_file_modal`, `open_file_modal`), создание узла (`create_entity_modal`),
  вход в правку объёма (`component_drawers.cpp`), создание и закрытие клипа,
  применение позы (`timeline_panel`), весь редактор машины (`fsm_panel`).
- **Инфраструктуры нет.** Нет JSON-библиотеки, сокетов, кодировщика
  изображений, чтения кадра, аргументов командной строки. Лог жёстко пишет в
  stdout, поэтому stdio-транспорт внутри `sculptor.exe` невозможен без правки
  `vw.core`.
- **Стартовая модалка блокирует команды** и закрывается только кликом.

## 2. Архитектура

```
Claude Code ──HTTP POST /mcp──► сетевой поток (127.0.0.1)
                                     │ очередь запросов
                                     ▼
              начало app::render ── разбор JSON-RPC ── обработчик инструмента
                                                            │
                                     слой действий (std::expected<…, error>)
                                                            │
                                  operation_manager / сервисы / asset::*
```

- **Транспорт.** Streamable HTTP на `127.0.0.1`, ответ обычным
  `application/json`, без SSE. Подключение — `.mcp.json` с `type: "http"`.
  Заголовок `Origin` проверяется. Сырые сокеты без сетевой библиотеки, в одном
  `.cpp` (`<winsock2.h>` под `_WIN32`, POSIX-сокеты иначе).
- **Сетевой поток.** Отдельный `std::jthread` принимает соединения и разбирает
  HTTP. Запрос уходит на главный поток через очередь «`std::queue` +
  `std::mutex`» (образец — `chunk_loader`), ответ возвращается тем же путём.
  `job_system` не используется: его полосы заняты террейном, светом и мешером.
  Сетевой поток ждёт ответ с таймаутом и при его истечении сам отвечает
  ошибкой.
- **Исполнение.** Только на главном потоке, в новом хуке `gfx::app::update`,
  который движок зовёт каждую итерацию цикла независимо от того, открылся ли
  кадр (раздел 2.1). Шаги обслуживания состояния после команды чинят его
  (грязные модели, мёртвые контексты, выделение, допустимость инструмента).
  Если открыт popup, идёт жест мыши, вставка или полёт камеры — ответ «редактор
  занят» с причиной.
- **JSON.** Свой `vw::json` в `vw.core` (раздел 2.2).
- **Слой действий.** Новая партиция (рабочее имя `:actions`): функции с
  валидацией и `std::expected`, которые зовут и MCP, и модалки. Один путь
  вместо двух.
- **Всё через `operation_manager`.** Правки агента видны сразу и отменяются
  пользовательским Ctrl+Z.
- **Партиция `:mcp`.** Сервер, диспетчер, инструменты. JSON-типы из интерфейса
  партиции не экспортируются.
- **Команды на несколько кадров.** Снимок вьюпорта отвечает не в том кадре, в
  котором запрошен, поэтому обработчик может вернуть отложенный результат.

### 2.1. Работа при свёрнутом окне

Агент должен работать и тогда, когда редактор свёрнут. Одного сетевого потока
для этого мало: команды исполняет главный поток, а он при свёрнутом окне
заперт.

- `renderer::recreate_swapchain` (`engine/gfx/src/render/renderer.cpp`) при
  размере кадра 0×0 крутит блокирующий цикл из `poll_events` и сна на 16 мс и
  не возвращается, пока окно не развернут.
- `engine::render` при неоткрывшемся кадре (`begin_frame` вернул `false`) не
  зовёт `app::render`.
- `world_->clear_changed()` идёт в конце каждой итерации, а
  `collect_dirty_models` читает `changed` только из `app::render`. Если просто
  пропускать кадр, метки изменённых объёмов потеряются, и сохранение оставит
  старый `.voxm`.

Правка движка:

1. Ожидание ненулевого размера уходит из `recreate_swapchain` в
   `engine::main_loop`: при свёрнутом окне цикл продолжает крутиться без
   рендера, со сном, но с обновлением мира и приложения.
2. У `gfx::app` появляется `update(float delta_time)`, вызываемый каждую
   итерацию после `world_->update` и до `begin_frame`.
3. В Sculptor шаги обслуживания из начала `app::render` (`collect_dirty_models`,
   `prune_contexts_`, `clipboard_service_.sync`, границы объёма, видимость,
   допустимость инструмента) переезжают в `app::update`, там же сливается
   очередь команд. В `app::render` остаётся только отрисовка.

Ограничения свёрнутого режима: снимок вьюпорта недоступен (нет swapchain) и
возвращает ошибку; меши на GPU не обновляются до разворачивания.

### 2.2. Свой JSON

Партиция `vw.core`, namespace `vw::json`. При написании сверяемся с устройством
существующих библиотек, прежде всего nlohmann-json: модель значения, различение
целых и вещественных, обработка `\u` и суррогатных пар, поведение на краевых
случаях.

- **Значение.** `std::variant` из null, `bool`, `int64`, `float64`, строки,
  массива и объекта. Целые и вещественные различаются, как у nlohmann.
- **Объект.** Вектор пар в порядке вставки: объекты малы, вывод детерминирован.
- **Разбор.** Рекурсивный спуск с пределом глубины,
  `std::expected<value, parse_error>` с позицией и сообщением. Исключений нет.
- **Числа.** `std::from_chars` и `std::to_chars`: кратчайшая запись с точным
  обратным чтением.
- **Запись.** Компактная и с отступами.
- **Доступ.** Поиск по ключу и типизированные чтения, возвращающие ошибку с
  путём до поля — из них собираются сообщения инструментов.
- **Проверка.** Тесты в `core_tests`, фаззер в существующей инфраструктуре
  `VW_BUILD_FUZZERS`, прогон набора соответствия JSONTestSuite.

Рукописный писатель в `engine/gfx/src/engine/report.cpp` можно позже перевести
на `vw::json`; в объём этой фичи это не входит.

## 3. Принципы инструментов

- **Явная адресация.** Узел по имени, клип по имени, ключ по тройке (трек,
  канал, время). Зависимости от выделения и курсора нет. `id` ключа наружу не
  отдаётся: он не переживает сохранение.
- **Контекст правки переключает сам инструмент.** `volume_*` входит в объём
  узла, `clip_*` — в клип. Пользователь видит в редакторе, что правит агент.
- **Пачками.** Один вызов — одна операция undo.
- **Сохранение только явное,** отдельным инструментом.
- **Ошибка говорит, что допустимо:** «узла `hand` нет; есть: …».

## 4. Набор инструментов

| Группа | Инструменты |
|---|---|
| Редактор | `editor_state`, `undo`, `redo`, `assets_list`, `palette_list` |
| Префаб | `prefab_new`, `prefab_open`, `prefab_save`, `prefab_save_as`, `prefab_close`, `prefab_get` |
| Узлы | `node_create`, `node_delete`, `node_move`, `node_set_transform`, `node_set_components`, `prefab_set_rig` |
| Объём | `volume_get`, `volume_write`, `volume_erase`, `volume_reshape`, `volume_set_pivot`, `volume_rename` |
| Клип | `clip_create`, `clip_open`, `clip_get`, `clip_set_keys`, `clip_remove_keys`, `clip_remove_track`, `clip_save`, `clip_close`, `clip_pose_at` |
| Машина | `fsm_create`, `fsm_get`, `fsm_set`, `fsm_save`, `prefab_set_machines` |
| Вид | `view_set`, `view_screenshot` |

Уточнения:

- `node_create` принимает роль: пустой объём заданного размера, объём из файла,
  сокет, точка.
- `node_set_components` покрывает сокеты, варианты, `anim_target`, `structure`,
  точки мебели и соединения.
- `volume_get` отдаёт размер, pivot, занятый бокс и срезы по Y текстом с
  легендой вокселей.
- `volume_write` принимает боксы, список вокселей и срезы; собирает
  `asset::voxel_clip` и исполняет одну `paste_voxels_operation`. Объём
  расширяется сам. Ответ возвращает новый размер и смещение координат.
- `volume_reshape` — обрезка, поворот, отражение, явный размер.
- `clip_pose_at` ставит позу клипа на момент времени, чтобы её можно было снять
  снимком.
- `fsm_set` заменяет документ целиком: `set_fsm_operation` уже так устроена.
  Нужна только валидация (уникальность имён, существование целей и клипов,
  entry).
- `view_set` — орбита вокруг узла (yaw, pitch, расстояние) и пресеты.

| 0c | Каркас | Сокет и сетевой поток, разбор HTTP, JSON-RPC (`initialize`, `tools/list`, `tools/call`), очередь, слив в `update`, `editor_state`, `.mcp.json`, индикатор в меню. Проверка сборки на MSVC, clang + MS STL, clang + libc++ | M |

результат. Этап 6 независим и может идти раньше.

## 6. Попутные дефекты

Агент наткнётся на них сразу, поэтому чинятся по ходу:

- `add_voxel_operation::undo` ставит воздух вместо прежнего значения.
- `delete_entity_operation` не обрабатывает детей; undo теряет `source` и
  компоненты.
- Открытие префаба идёт без `library.forget`: «Discard» не отбрасывает
  поштучные правки вокселей, они остаются в кеше `model_library`.
- `state.reset` не чистит `animation_clip_registry`.
- `fsm_service::create` перезаписывает существующий файл; вход в другую машину
  затирает несохранённые правки.
- Ctrl+S в контексте машины сохраняет префаб, а не машину.
- `remove_track_operation` не помечает клип несохранённым;
  `add_track_operation::undo` не снимает добавленный target-компонент.
- Снятие `structure_component` правит мир без операции и undo.

## 7. Риски

- **Системные заголовки сокетов перед `import std`** на трёх тулчейнах под
  `-Werror`. Прецедент — `<windows.h>` в `menu_bar.cpp`. Проверяется на
  этапе 0c.
- **`std::from_chars` для вещественных в libc++:** поддержка появилась недавно,
  на clang-20 проверяется первым делом на этапе 0a.
- **Правка главного цикла движка** затрагивает все приложения (arena, testbed).
  После этапа 0b — тесты и замер по навыку `render-bench`.
- **Сдвиг координат:** расширение объёма в минус двигает воксели и pivot.
  Координаты между вызовами, меняющими форму, не кешируются.
- **Клиент Claude Code:** поведение HTTP-клиента (GET-поток, заголовок сессии)
  проверяется на этапе 0.
- **Арена читает копию ассетов** рядом с бинарником: после правок нужна
  пересборка или копирование.
- **Знак углов:** `euler_to_quat` отрицает углы. Конвертация только функциями
  движка.

## 8. Принятые решения

- **JSON — свой**, `vw::json` в `vw.core`, с оглядкой на устройство
  nlohmann-json. Отклонены: nlohmann-json, yyjson, glaze (сторонняя
  зависимость и текстовые заголовки перед `import std`).
- **Сеть — сырые сокеты и отдельный поток.** Отклонены: cpp-httplib (огромный
  заголовок, свой пул потоков), mongoose (GPLv2), civetweb, asio и libuv (HTTP
  всё равно писать самим), опрос сокета из кадра (не работает при свёрнутом
  окне), stdio-мост на Python (лишний процесс).
- **Проект open source**, лицензионных ограничений на распространение
  редактора нет.
- **Включение сервера — и опция сборки, и флаг запуска.** Опция CMake
  `VW_SCULPTOR_MCP` решает, попадает ли сервер в бинарник; флаг `--mcp` решает,
  слушает ли он порт. Без флага порт не открывается. До кода опция доходит
  экспортированным `constexpr`, а `main` в Sculptor получает разбор аргументов.
- **PNG — `stb_image_write`,** спрятанный в одном `.cpp`: заголовок включается
  в его global module fragment, а наружу партиция `.cppm` отдаёт функцию с
  сигнатурой в стиле проекта (типы проекта, `std::expected`, никаких типов
  stb). Порт `stb` идёт в фичу vcpkg `gfx`.
- **Выделение, буфер и вставка закоммичены** до начала работ: этап 3 опирается
  на `paste_voxels_operation` и `replace_volume`.
