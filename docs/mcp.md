# MCP в Sculptor

Sculptor умеет принимать команды по Model Context Protocol: агент подключается
к запущенному редактору и правит то, что в нём открыто. Здесь устройство
сервера и контракт инструментов; как делать ими контент — навык
`sculptor-mcp`, как дописывать сервер — навык `sculptor`.

## Запуск и подключение

```
sculptor --mcp           # 127.0.0.1:17800
sculptor --mcp=18000     # другой порт
```

Без флага порт не открывается. Сервер попадает в бинарник при опции сборки
`VW_SCULPTOR_MCP` (по умолчанию `ON`); в сборке без него `--mcp` — ошибка
запуска.

Claude Code берёт адрес из `.mcp.json` в корне репозитория (`type: "http"`,
`http://127.0.0.1:17800/mcp`). Редактор должен быть запущен до подключения;
после перезапуска редактора достаточно переподключиться командой `/mcp` —
сеансов сервер не держит.

Состояние видно в правом углу строки меню: `MCP :17800 | N` — порт и число
принятых запросов, `MCP off` — сервер не слушает (причина в подсказке и в
логе).

**Порт занят — частый случай на Windows.** Система резервирует диапазоны
портов, и привязка к ним падает так же, как к занятому: на машине разработчика
закрытым оказался весь диапазон 47700–47899, хотя `netstat` и
`netsh int ipv4 show excludedportrange` его не показывали. Если сервер пишет
`port N is taken`, возьми другой порт флагом и поправь `.mcp.json`.

## Устройство

```
клиент ──HTTP POST /mcp──► сетевой поток: разбор HTTP, проверка Host и Origin
                                │ очередь (mutex + vector)
                                ▼
                app::update ── mcp::server::poll ── mcp::dispatcher ── инструмент
```

- **Сетевой поток** — `net::http::server` из модуля движка `vw.net`
  (`docs/ENGINE.md#сеть`); в самом редакторе сокетов нет. Он принимает
  соединение, читает один запрос, кладёт его в очередь и ждёт ответ от главного
  потока. Соединения обслуживаются по одному.
- **Главный поток** забирает очередь в `app::update`, то есть каждую итерацию
  цикла, в том числе при свёрнутом окне (`docs/ENGINE.md#главный-цикл`). Команда
  исполняется до шагов обслуживания состояния, и те в том же тике приводят
  документ в порядок.
- **Диспетчер** (`mcp/protocol.cpp`) разбирает JSON-RPC и зовёт инструмент.
  Сокетов и потоков он не знает.
- **Инструменты** (`mcp/editor_tools.cpp`) получают `mcp::editor_bindings` —
  указатели на движок и состояние редактора.

Партиция — `vw.sculptor:mcp`, пространство имён — `vw::sculptor::mcp`: всё, что
относится к серверу, живёт в нём и префикса в имени не носит. Наружу партиция
отдаёт только `mcp::server`, `mcp::editor_bindings` и `mcp::default_port`;
диспетчер, описание инструмента (`mcp::tool`) и разбор аргументов
(`mcp::argument_reader`) объявлены в том же `.cppm` вне `export`. Состояние
сервера для строки меню — `mcp::server_status` в `:state`. При
`VW_SCULPTOR_MCP=OFF` вместо остальных файлов `mcp/` собирается
`mcp/server_disabled.cpp` с пустым сервером.

## HTTP

Свой разбор, без библиотеки: задача — один локальный клиент. Разбор и отказы
до пути — дело `net::http::server`; путь, метод и JSON-RPC разбирает диспетчер.

| Запрос | Ответ |
|---|---|
| `POST /mcp` с `Content-Length` | ответ JSON-RPC, `application/json` |
| уведомление или ответ клиента | `202`, без тела |
| `GET`, `DELETE` на `/mcp` | `405`, `Allow: POST` |
| другой путь | `404` |
| `Host` или `Origin` не локальные | `403` |
| `Transfer-Encoding` в запросе | `411` |
| заголовки больше 16 КБ, тело больше 16 МБ | `431`, `413` |
| главный поток не ответил за 30 с | `504` |

- **Ответ всегда один и целиком.** Потока событий (SSE) нет, `GET` для него
  отклоняется — спецификация это разрешает.
- **`Connection: close` на каждый ответ.** Соединения не переиспользуются.
- **`Expect: 100-continue` поддержан:** его шлёт `curl` на телах больше
  килобайта.
- **Проверка `Host` и `Origin`** закрывает DNS rebinding: страница в браузере не
  может дотянуться до редактора, даже зная порт. Локальными считаются
  `127.0.0.1`, `localhost` и `[::1]`.
- Запрос, который не дождался ответа, помечается брошенным, и главный поток
  его не исполняет.

## Протокол

| Метод | Что делает |
|---|---|
| `initialize` | версия протокола, `capabilities.tools`, имя и версия сервера, краткая инструкция |
| `ping` | пустой результат |
| `tools/list` | имена, описания и схемы аргументов |
| `tools/call` | исполняет инструмент |
| `notifications/*` | принимаются без действия |

- Версия протокола: если клиент просит известную (`2025-11-25`, `2025-06-18`,
  `2025-03-26`, `2024-11-05`), сервер отвечает ею же, иначе `2025-06-18`.
- Пакеты (массив запросов) не принимаются: `-32600`.
- Сбой инструмента — не ошибка протокола: результат с `isError: true` и
  текстом, по которому агент может поправиться. Ошибкой JSON-RPC (`-32602`)
  отвечает только неизвестное имя инструмента или кривые `params`.

Результат инструмента — один текстовый блок с компактным JSON;
`view_screenshot` кладёт перед ним блок-картинку (`image/png` в base64).

**Занятость.** `editor_state.busy` — причина, по которой редактор сейчас не
примет правку, либо `null`. Причин четыре: идёт размещение вставки, зажата
кнопка мыши (жест гизмо, выделение, полёт камеры), активно поле ввода или
ползунок, открыт диалог. Стартовый диалог занятостью не считается: агент сам
открывает префаб, и диалог после этого закрывается. Правящий инструмент
оборачивается в `when_idle` и при занятости отвечает отказом с этой причиной;
читающие инструменты работают всегда.

**Несохранённое.** `prefab_new`, `prefab_open` и `prefab_close` отказывают,
если есть несохранённые правки префаба, клипа или машины, и называют, чьи они.
Отбросить их можно только явным `discard_unsaved: true` — диалога «Discard?»
у агента нет.

**Имена префабов.** Имя принимается с `.vox` и без него; разделители пути и
символы, недопустимые в имени файла, отклоняются. `prefab_new` и
`prefab_save_as` не перезаписывают существующий файл без `overwrite: true`.

**Узел читается и пишется в одной форме.** `prefab_get` и ответы `node_*`
отдают узел теми же полями, какие принимают `node_create` и
`node_set_components`:

| Поле | Значение |
|---|---|
| `position`, `rotation_degrees`, `scale` | относительно родителя; поворот — эйлеровы углы в градусах |
| `volume` | `{"size": [x, y, z]}` — новый пустой объём, `{"ref": "models/….voxm"}` — файл; в ответе ещё `pivot` |
| `anim_target` | имя цели для клипов; `true` при записи берёт имя узла |
| `sockets` | список целиком: `name`, `position`, `rotation_degrees`, `scale` |
| `variant` | `candidates` (`.voxm` или `.vox`) и `selected` |
| `structure` | `type`, `races`, `tier` 0–5, `size` из `S`, `M`, `L`, `XL` |
| `furniture`, `connection` | категория и профиль точки |

В `node_set_components` трогаются только названные компоненты; `null` снимает
компонент. `sockets` и `structure` заменяются целиком, а не по полю.

**Один вызов — один шаг undo.** `node_create` со всеми компонентами и
`node_set_components` с несколькими компонентами исполняются одной составной
операцией: `undo` снимает всё разом.

**Проверка до исполнения.** Операции редактора ошибок не возвращают, поэтому
всё проверяет `node_service` до того, как собрать операцию: существование узла
и родителя, уникальность имени узла, цели и сокета, допустимость имени (буквы,
цифры, `_`, `-`, `.`), размер объёма (сторона 1–256), загружаемость файла
объёма, существование кандидатов варианта, цикл при переносе. Отказ ничего не
меняет и в историю не попадает. Единственное исключение — вариант: применимость
кандидата-префаба выясняется только при постановке, поэтому сервис исполняет
шаг, сверяет выбранный индекс и при неудаче сам делает undo.

**Неизвестное поле — ошибка.** `mcp::argument_reader::allow` отклоняет поле,
которого нет в схеме инструмента, и перечисляет допустимые. Опечатка в имени
поля иначе молча игнорировалась бы.

**Контекст.** Инструменты узлов работают в контексте префаба и сами в него
возвращаются: из объёма и машины — `ctx.leave_to(0)`, из клипа — через
`clip_service::exit_animation_mode`, который возвращает узлам позы покоя. Иначе
правка трансформа записала бы позу клипа.

### Объёмы

**Координаты.** Воксель адресуется целыми `[x, y, z]` от `[0, 0, 0]` до
`size − 1`; `y` — вверх. Начало координат узла лежит в `pivot` объёма, поэтому
воксель `[x, y, z]` стоит в узле в точке `[x, y, z] − pivot`.

**Слои.** `volume_get` отдаёт воксели текстом, и `volume_write` принимает его
обратно без переделки:

```json
"layers": {
  "origin": [0, 0, 0],
  "legend": {"a": "gray_5", "b": "red_2"},
  "slices": [["aaaa", "aaaa"], [".bb.", "...."]]
}
```

`slices[k]` — слой `y = origin.y + k`, его строка `j` — `z = origin.z + j`,
символ `i` строки — `x = origin.x + i`. `.` — воздух, остальные символы
расшифровывает `legend`: имя вокселя из `palette_list` или его индекс. При
чтении символы раздаются по убыванию частоты, поэтому `a` — самый частый
воксель региона. Без `min` и `max` читается занятый бокс; регион больше
40 000 ячеек не отдаётся, вместо слоёв приходит `truncated` с просьбой сузить.

**Запись.** Один вызов `volume_write` — один шаг undo. Сначала применяются
`boxes` (углы включительно), затем `points`, затем `layers`; позднее
перекрывает раннее. Воксель задаётся именем, индексом или `"air"`. В слоях `.`
стирает ячейку; с `"air": "keep"` оставляет её как есть — так накладывают
деталь поверх готового. Предел — два миллиона ячеек на вызов.

**Границы строгие.** Запись за пределы объёма — отказ, а не молчаливое
расширение: расширение в отрицательную сторону сдвигает все координаты, и
агент рисовал бы дальше по устаревшим. Объём растят явно —
`volume_reshape` с `resize`, — и ответ называет `shift`: на сколько сдвинулся
каждый воксель. После `rotate` и `mirror` координаты переставлены, и вместо
сдвига приходит `note` с просьбой перечитать объём.

**Перекраска и симметрия.** `recolor` заменяет воксели одного вида другим во
всём объёме или в области и применяется первым; каждая запись читает объём
таким, каким он был до вызова. `symmetry` пишет каждую клетку дважды — как
задано и зеркально через плоскость, проходящую через pivot. Плоскость обязана
лежать на границе клеток или посередине клетки, то есть pivot по этой оси
кратен 0,5; иначе отказ. Обе половины — один шаг undo.

Сдвига содержимого отдельной командой нет, потому что он уже выражается
двумя существующими: относительно узла воксели сдвигает `volume_set_pivot`, а
внутри коробки — `resize` в `volume_reshape` (прибавить с одной стороны, убрать
с другой).

**Общий объём.** Несколько узлов могут ссылаться на один файл `.voxm`; правка
через любой из них меняет все. `volume_get` перечисляет остальных держателей в
`shared_with`; развести их — `volume_fork` (см. «Копия узла»).

**Контекст.** Правящие инструменты объёма сами входят в контекст объёма узла —
в редакторе видно, какой объём правит агент, — а инструменты узлов возвращают
редактор в префаб.

### Клипы

**Клип правится на открытом префабе.** Трек адресует цель — `anim_target`
узла, а не сам узел; цель, которой в префабе нет, отклоняется с перечнем
существующих. Несколько клипов могут быть открыты разом; инструменты берут
клип по `clip`, а без него — выбранный в редакторе. `editor_state` перечисляет
открытые в `open_clips`.

**Ключ — поза цели на момент времени.** Один ключ задаёт любые из `position`,
`rotation_degrees` и `scale`:

```json
{"target": "head", "time": 1, "position": [0, 12, 0],
 "rotation_degrees": [0, 45, 0], "interp": "ease_in_out"}
```

- Значения — трансформ узла относительно родителя, **абсолютный**, а не
  смещение от позы покоя. Свойство без ключей берётся из позы покоя.
- `interp` — как значение идёт от этого ключа к следующему: `linear`, `step`,
  `ease_in`, `ease_out`, `ease_in_out`, `cubic_bezier` (с `tangent_in` и
  `tangent_out`).
- Клип длится до последнего ключа; длительность отдельно не хранится.
- Зацикливание и скорость — не свойства клипа: их задаёт состояние машины.

**Один ключ на момент.** Ключ, поставленный ближе миллисекунды к имеющемуся в
том же канале, заменяет его (`asset::same_instant_seconds`). `clip_get`
поэтому адресует ключ тройкой «цель, канал, время», а не идентификатором:
идентификаторы ключей не переживают правку.

**`clip_get` сливает каналы в позы.** Ключи позиции, поворота и масштаба с
одним временем и одной кривой отдаются одной записью; если кривые у каналов
разные, записей на этот момент несколько. Каждую запись можно послать обратно
в `clip_set_keys`, добавив `target`.

**Правка — замена треков.** `clip_set_keys` и `clip_remove_keys` копируют треки
клипа, правят копию функциями `asset::put_key` и `asset::drop_keys` и
исполняют одну `set_clip_tracks_operation`. Поштучные операции редактора для
пачки не годятся: план каждой смотрит на клип до исполнения предыдущих, и два
ключа в новый трек создали бы его дважды.

**События — замена списка.** `clip_set_events` получает весь список
`{"time", "name", "payload"}` и исполняет одну `set_clip_events_operation`;
пустой список снимает все события. Правка того же вида, что у машины в
`fsm_set`: прочитать `clip_get`, поправить, отдать назад. Проверку делает
`clip_service::set_events` по `asset::find_problems`: имя — одно слово, данные —
одно слово или пусто, время — от нуля до последнего ключа. События клип не
удлиняют, поэтому ставь их после ключей. Если ключи потом укоротили клип,
`clip_get` и шкала времени покажут событие за концом в `problems`. Когда
событие срабатывает в игре — `docs/ENGINE.md#события-клипа`.

**Поза.** `clip_pose_at` ставит узлы в позу клипа на момент времени — для
`view_screenshot`. Это предпросмотр: выход из клипа возвращает позу покоя.
Инструменты узлов перед правкой сами выходят из клипа, иначе трансформ узла
записался бы позой.

**Раскадровка.** `clip_filmstrip` ставит позу, ждёт три тика, снимает кадр — и
так для каждого момента, а отдаёт одну картинку: кадры слева направо и сверху
вниз, по четыре в ряд (`gfx::tiled`). Моменты — `times` либо `frames` равных
долей клипа. Один вызов вместо пары `clip_pose_at` и `view_screenshot` на
каждый момент; вид берётся тот, что оставил `view_set`.

**Проигрывание.** `clip_play` запускает клип на его слое и отвечает сразу; клип
идёт дальше сам, в том числе при свёрнутом окне — анимацию двигает тик, а не
кадр. `from` задаёт момент старта, `loop` (`once`, `loop`, `ping_pong`) и
`speed` — повтор и скорость. Оба остаются за клипом до закрытия редактора: это
те же настройки сеанса, что правит шкала времени, в файл клипа они не
пишутся. `clip_stop` ставит клип на паузу в нуле и показывает его первую позу.
Состояние отдаёт `clip_get` полем `playback`: `state`, `time`, `loop`, `speed`.
Проигрывание — для человека у экрана. Агенту нужен кадр конкретного момента, а
снимок идущего клипа ловит случайный; для него остаётся `clip_pose_at`.

### Копия узла

`node_duplicate` копирует узел со всем поддеревом одной операцией
`duplicate_entity_operation`. Поле `names` называет каждую копию: по записи на
узел поддерева, ключ — имя оригинала. Недостающее имя — отказ с перечнем, а не
выдуманный суффикс.

- **Объём у копии свой.** Каждый скопированный узел получает собственную копию
  объёма без ссылки на файл; файл появляется при `prefab_save` и называется по
  узлу, как у объёма, заведённого размером. Общий с оригиналом объём был бы
  ловушкой: правка одной руки молча меняла бы другую.
- **Цель анимации копии называется по её узлу.** Имена целей в префабе
  единственны, дословно скопировать цель нельзя. Имя, уже занятое чужой целью,
  — отказ.
- **Имена сокетов сохраняются**, как и остальные компоненты. Клипы копия не
  получает и за собой не тянет.
- **`mirror`** — ось, перпендикулярно которой через начало координат родителя
  проходит плоскость отражения. Отражается всё разом: положение и поворот
  каждого узла копии, его сокеты и сами воксели (объём переворачивается вокруг
  pivot). Отражение всех локальных трансформов одной и той же плоскостью вместе
  с переворотом объёмов даёт точный зеркальный образ поддерева; проверено на
  гуманоиде — зеркальная копия правой кисти совпала с левой на снимке.
- Поддерево со слотом варианта зеркально не копируется: его кандидаты — файлы,
  отразить их здесь нечем. Корень не копируется вовсе: у префаба он один.

`volume_fork` — обратная операция для уже общего объёма (узел, созданный по
`volume.ref` чужого файла): узел получает копию под новым именем файла, прочие
держатели остаются с прежним объёмом. Объём, который никто не делит, не
разделяется — на это есть `volume_rename`. Файл пишется при `prefab_save`.

### Что видно, но не сохраняется

Два инструмента меняют вьюпорт, а не префаб: в историю не попадают, флаг
несохранённого не ставят, в файл не пишутся.

- `view_hide` скрывает узлы вместе с поддеревьями — тот же набор, что глазок в
  дереве узлов. Список заменяет прежний, пустой показывает всё; `prefab_get`
  отмечает скрытые полем `hidden`.
- `socket_preview` ставит в сокет другой префаб так, как его прикрепит игра, —
  посмотреть меч в руке и подвинуть сокет. Загрузка вынесена из панели сокетов
  в `preview_service`, панель зовёт его же. Узлы превью в `prefab_get` не
  попадают; сокет показывает файл полем `preview`.

Оба видит и пользователь: закончив, верни как было.

### Имена: три команды вместо одной

Узел, его цель анимации и дорожки клипов называются независимо, и каждое имя
меняет своя команда. Связки «переименуй узел и заодно всё остальное» нет
намеренно: скрытое следствие теряется, как только у узла появляется ещё одно
имя, о котором связка не знает.

| Что переименовать | Команда | Что остаётся как было |
|---|---|---|
| узел | `node_rename` | цель анимации, имя слота варианта, файл объёма |
| цель анимации | `node_set_components` с `anim_target` | имя узла, дорожки клипов |
| дорожку клипа | `clip_retarget` | цель в префабе, остальные клипы |
| файл объёма | `volume_rename` | имя узла |

- `node_rename` — одна операция `rename_entity_operation`. Имя узла живёт
  только в редакторе и в файле префаба, компонента имени в ECS нет; операция
  переписывает его везде, где редактор держит копию: обе карты сцены,
  выделение, корень, скрытые узлы, стек контекста правки, выделение и вставку
  в объёме, сохранённые позы покоя и ключи превью сокетов.
- Историю переименование не очищает. Прежние операции помнят старое имя, но
  отменяются они строго после отмены самого переименования, когда имя уже
  прежнее.
- После переименования цели клип, у которого осталась дорожка старой цели,
  открыт, но правке не подлежит: `clip_set_keys` отвергнет набор с чужой
  целью. `clip_retarget` проверяет только новую цель, поэтому клип с
  несколькими устаревшими дорожками чинится по одной.
- Клипы на диске за целью не следуют: каждый открывается, переводится и
  сохраняется отдельно.

### Машины состояний

**Машина заменяется целиком.** `fsm_get` отдаёт машину одним объектом,
`fsm_set` принимает его обратно: прочитать, поправить нужное, послать. Так
устроен и редактор — `set_fsm_operation` хранит машину до и после, — поэтому
один вызов есть один шаг undo, а вопрос «как назвать переход, чтобы его
поправить» не возникает.

```json
{"machine": "fsm/humanoid_action.voxf", "rig": "humanoid", "entry": "none",
 "params": [{"name": "attack", "type": "trigger"},
            {"name": "attack_chain", "type": "int", "value": 0}],
 "states": [
   {"name": "none", "clip": null, "playback": "loop", "rate": 1,
    "transitions": [{"to": "attack_1", "on": "attack",
                     "when": [{"param": "attack_chain", "op": "==", "value": 1}],
                     "blend": 0.08}]},
   {"name": "attack_1", "clip": "animations/a_humanoid_attack_1.voxa",
    "playback": "once", "rate": 1, "fade_in": 0.06, "fade_out": 0.2,
    "transitions": [{"to": "none", "wait_end": true, "wait_blend": true}]}],
 "any": []}
```

- **Параметры:** `float`, `int`, `bool` держат значение, `trigger` срабатывает
  на один тик. В рантайме все значения — `float32`: `bool` — 0 или 1, тип живёт
  только в файле. Игра сама пишет `speed`, `dir_x`, `dir_z` и `grounded`
  сущности, у которой есть намерение движения и твёрдое тело, — объявлены они в
  машине или нет. `dir_x` и `dir_z` — направление желаемого движения в системе
  персонажа (вправо и вперёд, единичный вектор), на месте оба 0.
- **Переход** срабатывает, когда выполнено всё названное: триггер `on`, условия
  `when` (`param`, `op`, `value`), `wait_end` — клип состояния доигран,
  `wait_blend` — смешивание в это состояние закончено. Переходы состояния
  проверяются по порядку; `any` — раньше них, из любого состояния.
- **Затухания** (`fade_in`, `fade_out`, `blend`) — число секунд либо объект
  `{duration, interp, tangent_in, tangent_out}`. `fade_*` гасят весь слой,
  `blend` смешивает клип прежнего состояния с клипом нового.
- **Состояние без клипа** допустимо. Слой при входе в него рантайм не трогает:
  гаснет он потому, что прежний клип `once` доиграл и отработал своё
  `fade_out`. Из состояния с зацикленным клипом в состояние без клипа слой не
  погаснет.
- **Слои.** Машина номер i в `prefab_set_machines` управляет слоем анимации i.
  Слой 0 — базовый, слои выше перекрывают его на целях, которые анимирует их
  клип.

**Проверка до записи.** `asset::find_problems` отклоняет машину, в которой имя
состояния или параметра не уникально или не одно слово, `entry` или цель
перехода не называет состояние, `on` называет не триггер, условие читает
необъявленный параметр или триггер, скорость не положительна, время
отрицательно. Редактор сверх того требует, чтобы клипы были файлами, а rig
совпадал с rig префаба. Рантайм на всё это молчит: переход в несуществующее
состояние просто никогда не срабатывает.

**Открыта одна машина.** `fsm_set` открывает машину, которую правит; пока у неё
есть несохранённые правки, править другую и открепить её нельзя — сначала
`fsm_save`. Диалога «отбросить» у агента нет.

**Файл машины создаётся мимо undo.** `fsm_create` пишет файл сразу; undo
снимает только прикрепление к префабу.

**Проигрывание.** `fsm_run` запускает все машины префаба так, как их исполняет
игра: машина i ведёт слой i, каждая — со своего `entry` и с параметрами по
умолчанию. Машина, открытая в редакторе, идёт с несохранёнными правками — их
можно проверить до записи. `fsm_drive` ставит параметры (`set`) и дёргает
триггеры (`fire`) и отвечает через три тика, когда переход уже случился;
`fsm_status` читает состояние, клип и время каждого слоя и значения параметров.

- В редакторе `speed`, `dir_x`, `dir_z` и `grounded` не заполняет никто: у корня префаба нет ни
  намерения движения, ни твёрдого тела. Роль игры играет тот, кто зовёт
  `fsm_drive`.
- Запуск живёт в контексте машины. Инструментов там нет: приложение не рисует
  и не слушает инструмент, которого контекст не разрешает, так что манипулятор
  узла в машине не появляется и поза не может утечь в префаб. До 02.10.2026
  это было не так: инструмент выбора узла оставался активным, и манипулятор на
  корне двигал префаб прямо из редактора машины.
- Правка префаба или клипа, выход из контекста и `fsm_stop` останавливают
  машины и возвращают позу покоя — остановка стоит в `leave_edit_contexts`, то
  есть раньше самой правки.
- Правка самой машины их не останавливает, а применяется на лету: машины
  пересобираются из нового описания, каждая остаётся в своём состоянии, если
  оно ещё есть, а параметры сохраняют значения. Так работают и панель, и
  `fsm_set`, и undo: раз в тик `fsm_service::sync_run` сравнивает открытую
  машину с той, из которой собран запуск. Пока тянется ползунок, сверка ждёт —
  иначе клип начинался бы заново на каждом кадре.
- Правка, с которой машина не собирается (переход без цели, условие без
  параметра), запуск не роняет: идёт последняя годная версия, а причина видна
  в окне запуска и в поле `note` у `fsm_status`.
- Клипы состояний берутся у открытых клипов, а остальные читаются с диска
  только на время запуска и в список открытых не попадают.
- В панели машины запуск — кнопка Run внизу; у запущенных машин своё окно
  Machine Run слева: состояние каждого слоя, поля параметров, кнопки триггеров
  и Stop.

**Частичная правка трансформа читает позу покоя.** `node_set_transform`
дополняет непереданные поля текущими значениями узла. Раньше он читал их до
выхода из клипа, и правка масштаба посреди позы записывала в префаб
анимированное положение. Теперь значения отдаёт `node_service::rest_placement`,
который сначала возвращает позу покоя.

### Удаление файлов

`asset_delete` удаляет файл с диска: префаб вместе с папкой его объёмов, клип
или машину. Отмены в редакторе нет — вернуть файл может только система
контроля версий. Поэтому удаление отказывает, пока ассет кому-то нужен, и
называет кому:

| Что | Отказ, если |
|---|---|
| префаб | он открыт; другой префаб называет его кандидатом варианта или держит его объёмы |
| клип | он открыт; его играет состояние какой-либо машины на диске |
| машина | её исполняет открытый префаб или любой префаб на диске |

Ссылки ищутся текстом в файлах `prefabs/*.vox` и `fsm/*.voxf`: форматы
текстовые, и ссылка в них — путь от корня ассетов. Имя, выходящее за свою
папку, — отказ.

**Имя файла нового объёма.** Объём без файла получает имя по узлу при
`prefab_save`: `models/<префаб>/m_<узел>.voxm`. Если это имя уже держит другой
узел или кандидат варианта, берётся `m_<узел>_2`, `_3` и так далее: раньше новый
объём молча перезаписывал чужой файл.

### Вид

**Камера.** `view_set` ставит камеру редактора так, чтобы цель заполнила кадр:
цель — узел со всем поддеревом либо весь префаб, её центр и радиус берутся по
занятым вокселям в мировых координатах. Сторона задаётся именем (`from`) или
углами:

| `from` | Камера стоит | yaw, pitch |
|---|---|---|
| `iso` | со стороны +x +y +z | −135°, −30° |
| `+x`, `-x` | справа, слева | −90°, 90° |
| `+z`, `-z` | со стороны +z, −z | 180°, 0° |
| `+y`, `-y` | сверху, снизу | наклон ∓90° |

Направление взгляда — `(sin yaw · cos pitch, sin pitch, cos yaw · cos pitch)`,
как у `gfx::camera`. Гуманоид смотрит в +z: его лицо видно с `+z`. Камера
общая с пользователем: `view_set` двигает то, что он видит.

**Проекция.** `projection` — `perspective` или `orthographic`; без поля
остаётся та, что стоит. Ортогональный вид рисует без перспективного сокращения:
с названной стороны каждый воксель — квадрат одного размера, и снимок с `-z`
совпадает с текстом слоёв клетка в клетку.

| | Перспектива | Ортогональная |
|---|---|---|
| чем задаётся кадр | `distance` — расстояние до цели | `height` — сколько вокселей в кадре сверху донизу |
| по умолчанию | сфера цели вписана в угол обзора | коробка цели вписана по высоте и ширине |
| в ответе | `distance` | `voxels_high`, `voxels_wide` |
| в ответе снимка | — | `pixels_per_voxel` |

Чужое поле — отказ, а не молчаливый пропуск: `distance` в ортогональном виде и
`height` в перспективном называют правильное поле. Логика живёт в
`view_service` — его же зовут пункты меню View и клавиши цифрового блока, так
что агент и человек получают один и тот же кадр. Переключение проекции
сохраняет высоту кадра на глубине центра префаба.

**Вид спереди зеркален тексту слоёв.** Проверено меткой в `x = 0`: на снимке с
`-z` она слева, и `x` растёт вправо, как символы в строке слоя; на снимке с
`+z` она справа. Сверху (`+y`) `x` растёт влево, `z` — вниз. Агент, рисующий
лицо по тексту, получит его отражённым, если не сверится со снимком; это
сказано в описании `view_set`.

**Снимок.** `view_screenshot` отдаёт кадр таким, каким его рисует редактор, по
умолчанию без панелей и без оверлеев (оси, гизмо, рамка объёма); `interface` и
`overlays` их возвращают. `max_size` — длинная сторона картинки, по умолчанию
1024. На один кадр панели исчезают и у пользователя: снимается то, что ушло на
экран.

- **Снимок ждёт мешей.** Правка вокселей доходит до экрана не сразу: набор
  изменений поднимается на следующем обновлении мира, меш строит воркер. Снимок
  поэтому ждёт три тика и пустой очереди мешей
  (`renderer::has_pending_meshes`) и только потом заказывает кадр. Сценарий это
  стережёт: снимок сразу после `volume_write` отличается от снимка до него.
- **Ответ отложенный.** Инструмент не может ответить в том тике, в котором
  вызван: кадра ещё нет. Он возвращает `tool_outcome::later` — функцию, которую
  сервер зовёт каждый тик, пока та не отдаст результат; соединение всё это
  время ждёт. Так же должен быть устроен любой инструмент, чей ответ зависит от
  будущих кадров.
- **Свёрнутое окно — отказ.** Swapchain при этом нет, рисовать не во что.
  Остальные инструменты при свёрнутом окне работают.

Как снимается кадр — `docs/ENGINE.md#снятие-кадра`.

**Вещественные числа** в ответах пишутся кратчайшей записью исходного
`float32`: `0.99`, а не `0.9900000095367432`, которое дало бы прямое
расширение до `float64`. Делает это `json_of(float32)`; новые инструменты
отдают координаты и размеры только через `json_of`.

Рецепт нового инструмента — в навыке `sculptor`, раздел «MCP».

## Принятые решения

- **JSON свой** — `vw::json` в `vw.core`, с оглядкой на nlohmann-json.
  Сторонняя библиотека тянула бы текстовые заголовки перед `import std` на трёх
  тулчейнах.
- **Сеть на сырых сокетах, отдельным потоком.** Отклонены cpp-httplib (огромный
  заголовок, свой пул потоков), mongoose (GPLv2), asio и libuv (HTTP всё равно
  писать самим), опрос сокета из кадра (молчит при свёрнутом окне), stdio-мост
  на Python (лишний процесс).
- **Сервер — и опция сборки, и флаг запуска.** `VW_SCULPTOR_MCP` решает, есть
  ли он в бинарнике, `--mcp` — слушает ли порт.
- **PNG — `stb_image_write`** за интерфейсом `gfx::encode_png`.
- **Объём не растёт сам,** запись за пределы — отказ: расширение в минус
  сдвигает координаты.
- **Пачка — одна операция замены.** Воксели (`asset::edited`), ключи
  (`set_clip_tracks_operation`) и машина (`set_fsm_operation`) меняются целиком
  одним шагом undo, а не набором поштучных операций: план поштучной смотрит на
  состояние до исполнения предыдущих.
- **Проверки — в сервисах,** не в инструментах и не в операциях:
  `node_service`, `volume_service`, `clip_service`, `fsm_service` возвращают
  причину отказа текстом, и ими же пользуются диалоги там, где они переведены.

## Открытое

Не сделано:

- слой клипа и его затухания из MCP: `clip_play` задаёт только старт, повтор и
  скорость;
- переименование цели анимации и перевод дорожки клипа в интерфейсе редактора:
  обе команды есть только в MCP, в окне редактора переименовывается лишь узел.

Не проверено:

- **Linux и libc++.** POSIX-ветка сокетов `vw.net`, `std::from_chars` для вещественных
  и порт `stb` там не собирались ни разу. CI это сейчас не ловит: он красный с
  25.08.2026, а локальный `master` не запушен.
- Снятие кадра на swapchain кроме `B8G8R8A8Srgb`.
- Вариант с кандидатом-префабом, `clip_open` с `ignore_rig`.
- Пути через UI, переведённые на общий код: диалоги New и Open, Delete узла с
  детьми, Remove у Structure.
- Изменённая машина состояний в арене.
- Окно Rename в дереве узлов: операция под ним проверена через MCP, само окно
  мышью не открывалось.
- В ортогональном виде: выбор под мышью, размер манипуляторов и ручек
  выделения, управление свободной камерой. Математика покрыта тестами камеры,
  мышью в окне это не пробовалось.
- Клавиши цифрового блока и пункты меню View: проверен общий с MCP сервис, а не
  сами нажатия.
- Превью в сокете из панели Sockets после переноса загрузки в сервис: проверен
  путь через MCP, кнопка панели не нажималась.
- Зеркальная копия узла с поворотом не вокруг одной оси и с неравным масштабом:
  сценарий проверяет поворот вокруг z, гуманоид — вокруг x.
- Панель машины после переделки 02.10.2026 проверена снимком окна со всеми
  раскрытыми разделами, а не мышью: правка полей, окно Machine Run и Ctrl+S
  руками не нажимались.

Дефекты редактора, которые агент может задеть:

- `add_voxel_operation::undo` ставит воздух вместо прежнего значения — на
  инструментах MCP не сказывается, они пишут через `edit_voxels_operation`;
- `remove_model_component_operation::undo` возвращает объём без ссылки на
  файл: undo снятия объёма через `node_set_components` теряет `ref`;
- `add_track_operation::undo` не снимает добавленный target-компонент;
- шкала времени, запись позы и инструмент позы считают, что цель называется
  так же, как узел: цель с другим именем из окна редактора не ключуется, а
  выбор её строки на шкале не выделяет узел. Через MCP таких ограничений нет;
- имя слота варианта при создании берётся с имени узла и дальше живёт само:
  `node_rename` его не трогает, а отдельной команды для него нет;
- диалог создания машины перезаписывает существующий файл, вход в другую
  машину из панели затирает несохранённые правки — программный путь в обоих
  случаях отказывает.

Пределы, взятые с запасом, а не измеренные: сторона объёма 256, два миллиона
ячеек на `volume_write`, 40 000 ячеек слоями на `volume_get`.

## Проверка

`python tools/mcp_smoke.py [--port=N] [--scenario]` — дымовой прогон по
запущенному редактору: рукопожатие, список инструментов, вызов, ошибки
протокола, отказы HTTP. С `--scenario` он ещё проходит инструменты префаба,
узлов и объёмов на временных префабах `_mcp_smoke*`, которые за собой удаляет:
открывает `p_humanoid`, сохраняет копию, собирает префаб из узлов с
компонентами, переносит, удаляет поддерево и сверяет, что undo вернул его в
точности, рисует объём боксами, точками и слоями, меняет его форму, правит
общий объём через второй узел и сверяет, что сохранённое читается с диска тем
же; наводит камеру и снимает кадр до и после правки; открывает клип, ставит и
убирает ключи, сверяет позу по трансформу узла и клип — с прочитанным с диска;
создаёт машину состояний, заменяет её, проверяет десять видов отказа и сверяет
машину с прочитанной с диска. При свёрнутом окне
проверки снимка заменяются одной: снимок обязан отказать. Сценарий закрывает то, что открыто
в редакторе, поэтому на рабочей сессии его не запускают.

Автотестов у приложения нет, поэтому скрипт гоняется руками после правок в
`mcp/`, на видимом и на свёрнутом окне.
