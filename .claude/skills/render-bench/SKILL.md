# Кадровые замеры testbed

Здесь то, как снять числа и как по ним судить. Что в кадре ещё стоит править и
какие числа считаются текущими — `docs/optimization-plan.md`.

## Сцена и путь камеры — две разные оси

`--scene=<имя>` говорит, что стоит в мире; `--camera=<путь>` — как по нему идёт
камера; `--bench` включает замер. Любую сцену можно пустить любым путём:

```
testbed.exe --scene=standing-lights --camera=orbit --bench --bench-frames=2000
testbed.exe --scene=blob-shadows            # свободный полёт мышью, без замера
```

Без `--bench` камера принадлежит человеку (`free`), и любую сцену можно облазить
руками. В замерном прогоне без `--camera` путь берёт сама сцена.

## Четыре вещи, без которых замер молча не состоится

**Значение отделяется только знаком `=`.** `arg_reader` (`apps/testbed/src/args.cppm`)
требует `--bench-frames=600`, а не `--bench-frames 600`. Разделённый пробелом
аргумент не парсится вообще, и опция тихо остаётся при умолчании. Сам `--bench` —
флаг без значения; забытый `--bench` означает, что приложение работает как
обычное окно и никогда не закрывается. Это первые подозреваемые, когда прогон
«завис» или померил не то.

**Запускать из каталога экзешника.** Шейдеры ищутся относительно рабочего
каталога: из корня репозитория приложение падает с
`failed to open file: shaders/voxel.vert.spv`.

**Окно должно быть на переднем плане.** Свёрнутое или перекрытое окно не
презентует, кадры не идут совсем: замерено — 0,03 с CPU за 5 секунд против
1,16 с за 6 секунд сразу после активации окна. Прогон при этом не падает, он
просто стоит. `run.ps1` держит окно активным сам.

**`--cluster-stats` и `--verify-lights` — не замерные прогоны.** Первый стоит
9 % CPU-кадра (обход 22080 счётчиков каждый кадр), второй строит эталон на CPU и
роняет кадр целиком. Числа из такого прогона несравнимы с обычными; берите из
него блок `clusters:`, а не таблицу стадий.

**И цена `--cluster-stats` растёт с числом кластеров, а не стоит на 9 %.** Обход
идёт по всем счётчикам, так что при `--cluster-tile=16` их 86 400 вместо 22 080:
замерено 188 fps против 466 на той же сцене, где без ключа обе конфигурации дают
одинаковый кадр. Свип по форме сетки поэтому делается двумя наборами прогонов —
занятость с ключом, время без него, — а не одним.

**Восстановленный из копии файл может не пересобраться.** Парный замер обычно
делают так: отложить правку, собрать, померить, вернуть, собрать, померить. Если
возвращать через `Copy-Item`, файл приезжает со **старой** отметкой времени —
той, что была у копии, — и ninja считает `.spv` или `.obj` свежее исходника и не
делает ничего. Сборка проходит без единой строки вывода, бенч отрабатывает, и
числа выходят полностью правдоподобные: это числа предыдущей сборки. Ловится
тем, что «после» совпадает с «до» до третьего знака. Возвращать содержимым
(`Get-Content -Raw | Set-Content`, `cat >`, любая перезапись), а не копией файла,
либо после копии сдвинуть `LastWriteTime` на текущее время.

Плюс условия сравнимости: сборка **Release**, режим представления **mailbox**
(при fifo замер упрётся в частоту монитора и покажет ровные 16,6 мс — такие
числа несравнимы ни с чем), и **первый прогон после сборки выбрасывается**: на
`voxel-edits` он давал frame p50 117,6 мс против 2,2 на следующем запуске той же
сборки.

## Готовый путь

```powershell
# до правки
pwsh .claude/skills/render-bench/run.ps1 -OutDir bench/before

# после правки
pwsh .claude/skills/render-bench/run.ps1 -OutDir bench/after

# вердикт по порогам
pwsh .claude/skills/render-bench/compare.ps1 -Before bench/before/terrain-parked.txt -After bench/after/terrain-parked.txt
```

`run.ps1` по умолчанию гоняет пустой рельеф четырьмя путями — `terrain:parked`,
`terrain:spin`, `terrain:walk`, `terrain:orbit`, — по 2000 замерных кадров с 200
прогревочными, и перед каждым делает один выбрасываемый прогон. Отчёт называется
по прогону: `terrain-parked.txt`. Параметры: `-Runs` (список вида
`сцена:камера`; имя без двоеточия — путь, назначенный сценой), `-Frames`,
`-Warmup`, `-Warmups`, `-Extra` (любые опции приложения как есть),
`-TimeoutSeconds`.

`compare.ps1` печатает таблицу «стадия / до / после / дельта % / вердикт» по
порогам протокола и предупреждает, если у отчётов разошлись сцена, путь камеры,
режим представления или число кадров.

**`-Extra` переживает только вызов в том же процессе.** `pwsh run.ps1 -Extra
"--moving-lights=256"` запускает новый процесс, массив по дороге разбирается
заново, до приложения опция не доходит — и сцена молча меряет умолчание. Так
была снята целая плоская кривая по числу источников, и выглядела она как
результат. Звать через `&`:

```powershell
& .claude/skills/render-bench/run.ps1 -Runs standing-lights -OutDir bench/x -Extra @('--moving-lights=256')
```

Проверять — по строке сцены в `testbed.log`: `standing-lights: N emitters
standing, M moving lights`. Если `M` не тот, что просили, замер не состоялся.

Вручную это выглядит так:

```
cd build/release/apps/testbed
./testbed.exe --scene=terrain --camera=parked --bench --bench-frames=600 --bench-out=parked.txt
```

## Сцены

| Сцена | Что ловит |
|---|---|
| `terrain` | голый рельеф: ничего не строит и ничего не правит, поэтому меряет ровно то, что покажет путь камеры |
| `voxel-edits` | цена правки: мир разбирается по вокселю после того, как всё осело |
| `lamp-edits` | цена правки, ставящей свет; парный контроль — `--inert` |
| `standing-lights` | установившийся свет: эмиттеры по поверхности плюс движущиеся источники |
| `clustered-lights` | то же самое, но источники в двух десятках плотных хуторов — сцена, на которой видно, что покупает деление по глубине |
| `blob-shadows` | кольцо тел, пятна под ними |
| `animated-crowd` | CPU: N тел с физикой и анимацией, 5N сущностей; `--bodies=200` заодно даёт двести пятен, то есть второй список сетки под нагрузкой |

## Пути камеры

| Путь | Что ловит |
|---|---|
| `parked` | статичный кадр, самая низкая дисперсия — число, которое сравнивают между сборками |
| `spin` | камера стоит и вращается: цена поворота, отсечение под нагрузкой |
| `walk` | ходьба по прямой без остановки: стриминг всё время замера |
| `orbit` | облёт по окружности радиуса 1500: стриминг плюс хвосты p95/p99 |
| `free` | мышь и клавиши; с `--bench` запрещён — путь у каждого прогона был бы свой |

`walk` и `orbit` трогаются с места только после того, как мир вокруг старта
готов: выход с холодного старта мерил первые восемьсот кадров догона.

Умолчания сцен: `spin` с наклоном −20° у обеих световых, `spin` с наклоном −25°
и вчетверо медленнее у пятен, `parked` со стороны и разворотом у толпы, `parked`
у рельефа и обеих правок.

Значение, не совпавшее ни с одним именем, — ошибка: стенд печатает список
известных имён и выходит. Раньше оно молча давало облёт пустого рельефа, и
опечатка была не ошибкой, а другой сценой.

**Движущиеся источники ходят по-разному в замере и без него.** С `--bench` орбита
шагает по номеру кадра: сцена, которую ведут по стенным часам, на каждой машине
разная, и мерить её нельзя. Без `--bench` она шагает по времени, шестьдесят
шагов в секунду — то же самое движение с той скоростью, с какой его показал бы
монитор. Иначе при шести сотнях кадров в секунду источник обходит весь диск
быстрее секунды и разглядеть в нём нечего.

`--light-speed` умножает и то, и другое. Ниже единицы — чтобы рассмотреть один
источник на границе тайла; в замерном прогоне эта опция означает, что померена
другая сцена, и числа несравнимы с записанными.

`voxel-edits` и `lamp-edits` ждут, пока мир осядет, **намеренно**: они меряют
цену правки в устоявшемся мире. Остальные сцены ставят своё содержимое по мере
готовности колонок.

## Опции

| Опция | Умолчание | Что делает |
|---|---|---|
| `--scene=<имя>` | `terrain` | что стоит в мире |
| `--camera=<путь>` | `free`, а с `--bench` — путь сцены | как идёт камера |
| `--bench` | выкл | замерный режим: 2000/200 кадров, шаг 1/60 с, отчёт |
| `--bench-frames=N` | 2000 | замерных кадров |
| `--bench-warmup=N` | 200 | прогревочных кадров после готовности сцены |
| `--bench-out=путь` | stdout | куда писать отчёт |
| `--bench-json=путь` | нет | тот же отчёт деревом JSON |
| `--bodies=N` | 50 у толпы, 8 у пятен | тел в `animated-crowd` и в `blob-shadows` |
| `--voxels-per-frame=N` | 1 | правок за кадр в `voxel-edits` |
| `--lamps-per-frame=N` | 1 | ламп за кадр в `lamp-edits` |
| `--inert` | выкл | контрольный прогон `lamp-edits`: тот же воксель, но не светящий |
| `--emitters=N` | 400 | стоящих эмиттеров в световых сценах |
| `--moving-lights=N` | 64 | движущихся источников там же |
| `--emitters-per-frame=N` | 1 | эмиттеров за кадр, пока световая сцена расставляется |
| `--hamlets=N` | 24 | хуторов в `clustered-lights` |
| `--light-speed=X` | 1 | во сколько раз быстрее ходят движущиеся источники |
| `--max-visible-lights=N` | без предела | предел источников, доживающих до пиксельного цикла |
| `--no-clusters` | выкл | старый путь: пиксель обходит все источники кадра, без froxel-сетки. Без `--max-visible-lights` это теперь сотня источников на пиксель — так и задумано, но это не «нормальный» прогон |
| `--cluster-tile=N`, `--cluster-slices=N`, `--cluster-cap=N` | 32 / 24 / 32 | форма сетки. `--cluster-slices=1` — это ровно плоские тайлы |
| — | 16 | предел списка кругов под ногами живёт в `cluster_settings::blob_cap`, ключа нет |
| `--cluster-stats` | выкл | вычитка `counts` каждый кадр: занятость сетки и переполнение. Печатается в **stdout**, не в `--bench-out` |
| `--verify-lights[=N]` | выкл (N=60) | раз в N кадров сверяет списки GPU с эталоном `vw::spatial` |
| `--mesh-workers=N`, `--terrain-workers=N` | 0 | размеры очередей; 0 — умолчание движка |
| `--chunk-cull` | выкл | отсечение по связности чанков |
| `--sun` | выкл | солнце ходит по небу; числа с ним несравнимы с остальными |

## Что в отчёте

Шапка: `gpu`, `build`, `present mode`, `frames in flight`, `warmup frames`,
`samples`, `fps at median frame`. Дальше три таблицы `p50 / p95 / p99 / max` —
CPU-стадии, системы мира (`system (ms)`) и `gpu_*`, — и блоки сводок:

- `meshing:` — чанки, квады, время на чанк, глубина и пик очереди;
- `terrain:` — то же по колонкам;
- `sky light:` — колонки, `rows/flood/bake`, `relight` после правок и бэклог;
- `scene ready after N frames, X ms`;
- `grid:` — сколько чанков загружено, сколько нарисовано;
- `pages:` и `memory:` — страницы пула, RAM, commit, VRAM;
- `buffers by size class` — слоты геометрии и их заполнение.

**Таблица `system (ms)` разбирает `world_update` по системам.** Строка на каждую
систему кортежа `world::systems`, в порядке кадра и под именем, которое система
носит сама. Сумма строк — это `world_update` из таблицы выше, поэтому выросший
`world_update` без выросшей строки здесь означает, что подорожал не шаг систем.
`compare.ps1` сравнивает их наравне со стадиями.

Строки `cascades drawn`, `grid_pending`, `grid_staged` в таблице — счётчики, а
не миллисекунды; процент от них ничего не значит, но разошедшийся счётчик
означает, что сравниваются две разные сцены.

**Блок `stand:` называет прогон.** Сцена и путь камеры выбираются порознь, и по
имени файла уже не сказать, чей это отчёт, поэтому стенд пишет их сам — `scene:`
и `camera:`. На них и ругается `compare.ps1`, если сравнивают разное.

**Блоки сцен попадают в отчёт наравне с кадровыми таблицами.** Сцена отдаёт свои
числа через `collect_report`, а движок спрашивает её до записи файла, поэтому
`voxel-edits:`, `lamp-edits:`, `standing-lights:`, `crowd:` и `clusters (…)`
лежат в `--bench-out` внизу, за таблицами. Перехватывать stdout больше незачем.

**`crowd:` говорит, толпу ли померили.** `grounded` меньше `bodies` означает, что
замер начался по предохранителю, а не по готовности: кто-то так и не встал на
землю, и в кадре была работа падения, а не стояния. `drift` — самый большой снос
тела от своей клетки; тела здесь стоят, поэтому у здоровой сцены он около нуля, а
выросший означает, что коробки расталкивают друг друга или их толкает рельеф.

**`--bench-json=путь` пишет тот же прогон деревом.** Шапка (`run`), все стадии с
p50/p95/p99/max (`stages`), системы (`systems`), сводка мешинга и блоки сцены —
теми же числами, что и в тексте, но без разбора таблиц регулярками. Текст остаётся человеку и
`compare.ps1`.

Лог рядом с экзешником (`testbed.log`) — про сцену, а не про время:
готовность камеры, `standing-lights: N emitters standing, M moving lights`,
`blob-shadows: N bodies of M asked`, `animated-crowd: N bodies of M parts each`.
Если чисел меньше, чем просили, сцена мерила не то, что заявила.

## Как читать

**CPU-стадии меряют запись команд, `gpu_*` — исполнение.** Они не суммируются и
не сравниваются между собой.

**`begin_frame` — это ожидание, а не работа.** Рост там при неподвижном
`gpu_frame` означает, что кадр упёрся в GPU или в состояние машины.

**Кадровое время имеет режимы, которые держатся десятками минут.** Записанный
случай: `terrain:parked` перешёл с 1,35 на 1,82 мс и просидел там около часа без
единой правки в эту сторону, а `gpu_world_geometry` через это окно не шелохнулся.
Отсюда два следствия: замеры «до» и «после» снимать **подряд**, а если CPU-время
поехало при стоящих `gpu_*` — это машина, а не правка.

**Считать кадры, а не миллисекунды**, там где есть выбор: `scene ready ms`
гуляет от 471 до 990 между прогонами одной сборки, а число кадров устойчиво.

**Мешинг и генерация не видны в кадровых процентилях** — они на своих потоках.
Для них есть блоки `meshing:` и `terrain:` с временем на чанк и на колонку.

Куда смотреть под конкретную правку:

| Правка | Метрики |
|---|---|
| шейдер, освещение | `gpu_world_geometry`, `gpu_world_pass`, `gpu_frame` |
| отсечение, indirect | `gpu_compute_cull`, `world_pass_geometry` |
| мешер | `meshing:` — время на чанк, число квадов |
| генерация, стриминг | `terrain:`, `scene ready after N frames`, пики очередей |
| запекание света | `sky light:` — `flood`/`bake`, `relight ... backlog` |
| память, форматы | `pages:`, `memory:`, `buffers by size class` |
| CPU-системы | `world_update`, `app_render` на `animated-crowd` |

## Пороги и приёмка

Три прогона на сцену, берётся медиана по p50 и по p99. Воспроизводимость на
неизменной ревизии известна: 0,15 % (`terrain:parked`), 0,44 % (`terrain:orbit`).

Порог значимости: **p50 — 2 %, p99 — 5 %, GPU-стадии — 3 %.** Дельта внутри
порога значит «эффекта нет», а не «стало чуть лучше».

Правка принимается, когда:

1. целевая метрика улучшилась не меньше, чем заявлено;
2. ни одна другая не ухудшилась сверх порога;
3. картинка не изменилась — там, где правка не про картинку;
4. `ctest` зелёный;
5. числа приложены к правке таблицей «до/после» — в описании коммита или в
   разделе `docs/optimization-plan.md`, если правка закрывает его пункт.

Если эффекта нет — правка либо откатывается, либо принимается отдельно и явно
как упрощение кода, с пометкой «perf-нейтрально».
