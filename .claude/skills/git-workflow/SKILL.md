# Git в voxelworld

## Кто что делает

**Читающие команды агент выполняет свободно:** `status`, `diff`, `log`, `show`,
`blame`, `rev-list` — они нужны, чтобы понять состояние работы.

**Коммит и создание ветки — только по прямой просьбе пользователя.** «Закоммить»,
«сделай ветку», «зафиксируй это» — просьба есть, действуем. Задача вида «почини
баг» или «сделай фазу M4» просьбой не является: закончив работу, агент показывает
итог и готовую рекомендацию (текст сообщения и список файлов), а решение
коммитить принимает пользователь.

То же правило для остальных изменяющих операций: `push`, `merge`, `rebase`,
`reset`, `checkout` с потерей изменений, `stash`, `tag`. Разрушающие (`reset
--hard`, `push --force`, `checkout --` поверх правок) — только если пользователь
попросил именно их, и стоит вслух назвать, что будет потеряно.

Причина простая: пользователь хочет сам просматривать диффы и держать историю
чистой, а не разгребать «всё подряд одним куском».

## Формат

**Сообщение коммита — по-английски,** `область: описание` в повелительном
наклонении. Области: `engine`, `sculptor`, `docs`, `shaders`, `build`.

```
engine: de-templatize ECS onto a concrete registry
build: move the spike recipes into cmake/
```

Тело сообщения (если правка нетривиальная) объясняет **почему**, а не
пересказывает диффа. Упомянуть измеренные последствия, если они есть, и честно
назвать то, что не получилось.

Подпись в конце:

```
Co-Authored-By: Claude Opus 5 <noreply@anthropic.com>
```

**Ветки — `kebab-case`:** `fix-shadow-artifacts`, `add-rotate-tool`,
`modules-migration`.

## Перед коммитом

Убедись, что тесты зелёные (навык `cmake-build`), и что в правке нет мусора:
временных файлов, комментариев и закомментированного кода, отладочных логов.
Объяснение «почему» для правки пишется в тело коммита, а не в код. Не пропускай хуки
(`--no-verify`) — если хук падает, чини причину.
