# C++ в voxelworld

## Стиль

**Trailing return type — всегда:**
```cpp
[[nodiscard]] auto get_value() const -> int32;
auto operator=(const foo&) -> foo& = delete;
```

**Типы проекта вместо встроенных и std:** `uint8..uint64`, `int8..int64`,
`float32`, `float64` (из `vw.core`). `int`/`float` в новом коде не пишем.

**Именование:** типы, функции, методы, поля, константы — `snake_case`; параметры
шаблонов — `PascalCase` (`T`, `Cs`); пространства имён — `vw::`, `vw::spatial::`,
`vw::asset::`, `vw::ecs::`, `vw::plat::`, `vw::gfx::`, `vw::sculptor::`.

**Приватные поля — с подчёркиванием в конце** (`world_`, `entity_`), приватные
методы — тоже (`update_entity_`), если это деталь реализации класса.

**Комментариев в коде нет.** Правило действует везде: C++, GLSL, CMake, Python,
CI.
- Код говорит о себе сам. Назначение видно из имени сущности. Единицы измерения
  и системы координат тоже записываются в имени или типе: `world_units_per_voxel`,
  а не `scale // мировых единиц в вокселе`. Упакованные поля раскладываются по
  структуре с именованными членами. Если без пояснения код непонятен, чинить
  нужно имя, а не добавлять комментарий.
- Для нетривиального алгоритма, замеренного решения, контракта между модулями
  (C++ ↔ шейдер, формат файла) или ловушки, которую не ловят тесты, пишется
  раздел в `docs/`. В коде остаётся максимум одна строка со ссылкой:
  `// см. docs/lighting.md#небесный-свет`.
- История решений («раньше было…», «пробовали X») принадлежит сообщению коммита.
  Замер, который иначе переоткроют, идёт в `docs/optimization.md`.
- Имя неиспользуемого параметра не прячется в `/*dt*/`: параметр остаётся
  безымянным.
- NEVER закомментированный код — его хранит git.
- Служебные комментарии допустимы:
  - ссылка `// см. docs/…`;
  - `} // namespace …` (его ставит clang-format);
  - пустой `//` в конце строки, который удерживает перенос от clang-format;
  - `// clang-format off` / `on` и `NOLINT`.

Правило проверяет `python scripts/lint_modules.py`.

**Инициализация:** конструктор вместо `init()`/`setup()`. Зависимости приходят
параметрами конструктора, а не сеттерами.

**Ошибки:** исключение — фатальный путь (нарушение инварианта), ловится только на
границе `main()`. Обрабатываемые ошибки — `std::expected`. В горячих путях
исключений нет.

**Заголовков у нас больше нет.** Единственный `#include` в репозитории — сторонняя
библиотека (`<imgui.h>`, `<catch2/...>`) либо сгенерированный CMake
`<sculptor_version.h>`; всё своё приходит через `import`. Сторонний заголовок
всегда идёт в global module fragment (`module;`) и всегда до импортов.

## Модульный код (движок и приложения)

Раскладка: компонент = каталог со своим `CMakeLists.txt`, исходники в `<lib>/src/`,
разложенные по смысловым подкаталогам (`world/src/systems/`, `gfx/src/render/`);
в корне `src/` лежит только первичный интерфейс модуля. Интерфейсные `.cppm` и
имплементационные `.cpp` одной сущности лежат рядом. Деления `include/` vs `src/`
нет — публичность выражается `export`.

Имя партиции повторяет каталог: `:systems.transform`, `:render.shadow_map`.
Партиция, собирающая другие, — агрегатор: только `export import`, без кода.

- Партиция = один `.cppm`. Взаимно зависимые сущности обязаны лежать в одной
  партиции: циклы между партициями запрещены (поэтому `math` и `transform`
  вместе, и вся геометрия `aabb`/`ray`/`plane`/`frustum` тоже).
- Внутри одного модуля форвард-объявление между партициями законно (`class world;`
  в `:systems`, определение — в первичном юните). Снаружи модуля объявлять его
  сущности нельзя — только импортировать.
- Интерфейс в `.cppm`, реализация нешаблонного кода в `.cpp`. `.inl.h` в модульном
  коде не бывает.
- В интерфейсной партиции остаются: шаблоны, `constexpr` и тела, которые зовут
  пер-воксельно или пер-узлово (`model::get_voxel`, аксессоры компонентов,
  `aabb::intersects`). Через границу модуля инлайнится только то, чьё определение
  лежит в интерфейсе — это измерено бенчмарком в M2.
- В `.cpp` не пиши `inline`: определение обязано быть единственным.
- От других модулей прячет `export`, а не `namespace detail`. Деталь, которую зовут
  шаблоны интерфейса, объявляй вне `export`-блока (образцы — `log::detail::emit`,
  `ecs::detail::invoke_on_add`): внутри модуля имя видно, импортёру — нет. То, что
  интерфейсу не нужно вовсе, — в `.cpp` в анонимное пространство имён (образец —
  проверки каталога в `voxels/catalog.cpp`). Анонимное пространство имён в `.cppm`
  не годится: экспортированный шаблон не вправе ссылаться на внутреннюю линковку.
- Стандартная библиотека — `import std;` везде: и в экспортируемых партициях, и в
  имплементационных юнитах. Текстуально `<vector>` и родню не включаем нигде:
  в одном TU `import std` и тот же заголовок текстом не уживаются.
- Макросы `import std` не даёт. `offsetof`, `assert`, `FLT_MAX` требуют либо
  `<cstddef>`/`<cassert>` в global module fragment, либо замены
  (`std::numeric_limits`). Предпочитай замену.
- Логирование — `import vw.core;` и `vw::log::info(...)`; категория задаётся
  `constexpr log::log_category lc_{"имя"}` в анонимном пространстве имён юнита.
- Колбэк стороннего C-API с точной сигнатурой держи в имплементационном юните:
  интерфейс объявляет `friend struct detail::<name>_callbacks`, определение
  живёт в `.cpp` (образец — окно и GLFW).
- Настройки сборки доходят до кода экспортированным `constexpr`, а не макросом
  (образец — `vw::log::min_level`). Макрос в заголовке потребителя ломает ODR,
  если TU соберут его по-разному.

Гигиену проверяет `python scripts/lint_modules.py` (он же в CI): ни одного
`#include` своего заголовка, ни одного `.inl.h`, C API Vulkan только в
`renderer.cpp` (граница ImGui) и `window.cpp` (граница GLFW), `vk::` только
внутри `vw.gfx`, `vk::detail` — только в `vulkan_context.cpp`, ни одного
`namespace detail` внутри `export` в `.cppm`, ни одного комментария, кроме
служебных, в C++, шейдерах, CMake, CI и скриптах.

## Рецепты

**Новый компонент ECS:** структура в подходящем
`engine/world/src/components/<group>_component.cppm` (новая группа — новая
партиция `:components.<group>` плюс строка в агрегаторе `components.cppm`),
namespace `vw::ecs`, приватные поля + аксессоры, дружба с системой, которая их
меняет. Тела аксессоров — прямо в классе. Отдельная регистрация не нужна:
идентификатор выдаётся лениво по первому обращению.

**Новая система ECS:** объявление в новой партиции
`engine/world/src/systems/<name>_system.cppm` (`export module
vw.world:systems.<name>;`), строка в агрегаторе `systems/systems.cppm`, тело —
`engine/world/src/systems/<name>_system.cpp` (`module vw.world;` + `import std;`).
Оба файла добавить в `engine/world/CMakeLists.txt`: `.cppm` в `FILE_SET
CXX_MODULES`, `.cpp` в `PRIVATE`. Систему включить в кортеж `world::systems` в
`world.cppm`. Необязательные хуки `on_add<C>`/`on_remove<C>`/`shutdown()`
подхватываются концептами автоматически.

**Система вне движка (игра, приложение):** тот же класс — `system_name`,
конструктор от `world&` и своих зависимостей, `update(float32)`, — но в кортеж он
не входит, а ставится в мир вызовом `world.add_system<S>(ecs::tick_stage::…,
args...)`. Все вызовы `add_system` модуля лежат в одной функции: порядок строк и
есть порядок тика внутри стадии. Хуки объявляются списком `using
observed_components = ecs::component_list<…>;` плюс шаблонные `on_add<C>` /
`on_remove<C>`. Компонент такой системы следует тому же рецепту, что и компонент
движка: приватные поля, дружба с системой-владельцем, запись через её
модификатор, который зовёт `request_change` или `notify_changed`. Системы
ставятся до создания сцены. Контракт наборов, стадии и сторож порядка —
`docs/ENGINE.md#расширение-мира` и `#кто-какой-набор-читает`.

**Пер-кадровый обход:** `registry::for_each<Cs...>(fn)`, а не `view`: 0,32 мс
против 0,50 мс на проход по 160 000 сущностей с парой компонентов. Разница —
цена итераторной обёртки, не стирания типа.

**Правка формата ассета** (`.vox`, `.voxm`, `.voxa`, `.voxf`, код в
`engine/asset/src/serial/`). Версия — константа `<формат>_file_version`:
`vox_file_version` и `voxa_file_version` в `vox_format.cppm`,
`voxm_file_version` в `voxm_format.cppm`, `voxf_file_version` в
`voxf_format.cppm`. Писатель ставит её в шапку (`# Voxm File Version 4.0`).
Читатель через `detail::major_version_differs` (`version.cppm`) сверяет только
мажор: минор не проверяется, файл без шапки читается без проверки.
- Добавил команду или поле, которые старый разборщик пропустит (неизвестную
  команду он пишет в лог и идёт дальше), — подними минор.
- Существующие числа или команды поменяли смысл — подними мажор. Тогда файл
  старой версии откажется читаться (`unsupported_version`), а не прочтётся
  молча по-новому. Образец — `.voxm` 2.0: номера набора для покраски стали
  цветами палитры.
- После подъёма мажора сам переведи файлы в `assets/` на новый смысл и новую
  шапку. Старый мажор не откроют ни редактор, ни арена, так что пересохранить
  файлы через редактор уже не выйдет. Обнови строки версии в
  `tests/asset/serial.test.cpp` и `voxf_format.test.cpp`, добавь тест на отказ
  прежнего мажора и прогони `asset_tests`.

Рецепты инструмента и операции Sculptor — в навыке `sculptor`.
